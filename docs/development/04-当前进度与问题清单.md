## 2. 当前核心断点与新并行风险

现有主业务断点全部交给 A 处理；新增用户体系交给 B 独立开发。真正需要警惕的是：两条线分支同时开发时，不要在共享文件上互相覆盖。按严重程度排序：

### 🔴 断点 1：`/api/chat` 没有调用任何智能体（最致命）

- **现象**：`routes/chat.py`（A）只调 `scheduler.route()` 做意图分类，然后 `build_reply()` 返回**写死占位**。
- **而**：`agents/maintain.py`（B）已用 LangGraph + RAG 完整实现报价审核，`handle()` 可直接产出真实结论——**但从未被任何代码调用**。
- **后果**：咨询页给不出真实诊断。产品最核心的价值未交付。
- **本质**：旧分工里 A 留了"阶段 2 由 B 接入"的占位，B 把智能体写在了独立模块，但**没有人把两者接起来**。新分工下，这条主链路由 A 统一收口。
- **修复方向**：在 `chat.py` 路由命中后调用对应智能体的 `handle(text, context)`，用真实返回填充 `reply/steps/price_*`。详见 [05](./05-任务清单与开发计划.md) 任务 A-T1。

### 🔴 断点 1.5：`maintain` 接入不是纯粹"前端零改动"

- **现象**：`agents/maintain.py` 的真实输出包含当前前端契约没有列出的值：`steps[].status = "miss"`、`blocks[].type = "good"`。
- **而**：`utils/request.ts` 里 `ChatStep.status` 只允许 `done|doing|pending|todo`，`ChatBlock.type` 只允许 `kv|warn|danger`。WXML 对 `good` 类型也没有专门分支，只能依赖 `b.good` 布尔值着色。
- **后果**：运行时未必立刻崩，但类型契约已经不一致，后续一旦开启更严格的 TS 检查、复用类型写逻辑或扩展渲染，就容易出问题。
- **修复方向**：A-T1 接入 maintain 时同步做输出规范化：后端把 `miss` 映射为前端已有状态，`good` 映射为 `kv + good:true`；或者同步扩展前端类型与渲染。本文档建议优先后端规范化，减少前端改动面。

### 🔴 断点 2：只有 maintain 一个智能体，dtc/symptom/part 仍是占位

- **现象**：scheduler 能把意图路由到 dtc/symptom/part，但这三个智能体**根本不存在独立实现**，回复写死在 `chat.py` 的 `build_reply()` 里。
- **后果**：即便接通断点 1，也只有"报价审核"类问题能得到真实答案；占小程序入口大头的"故障码""症状"类问题仍是占位。
- **修复方向**：参照 `maintain.py` 的 `handle()` 契约，新建 `agents/dtc.py`、`agents/symptom.py`、`agents/part.py`，复用 `services/rag.py` 检索对应知识库。任务 A-T3/A-T4/A-T7。

### 🟠 断点 3：`user_id` 发了但没接，上下文/存根全断

- **现象**：前端 `ChatPayload` 带 `user_id`（写死 `test_user_001`），后端 `chat.py` **不读取**；前端 chat/index/profile/receipt 的车辆信息和存根**全部写死**，从不调 `/api/context`、`/api/receipt`。
- **后果**：① 对话无法关联车辆上下文；② 诊断结论无法沉淀维修记录；③ "数据闭环"这一产品卖点无法实现。
- **修复方向**：chat.py 读取并透传 `user_id` → 智能体；前端 index/chat 顶部车辆卡片改调 `GET /api/context`。任务 A-T5。

### 🟡 断点 4：知识库「一键咨询」参数未传通

- **现象**：kb 页跳 `chat?ask=xxx`，但 `chat.ts` 的 `onLoad` 未取 `ask` 参数。
- **后果**：从知识库点"咨询"进对话，问题没带过去，需用户重打。
- **修复方向**：`chat.ts onLoad` 解析 `ask` 并回填/自动发送。任务 A-T6。

### 🟠 断点 5：最新原型要求取消 tabBar，当前代码仍是旧导航

- **现象**：当前代码已经加入原生 `tabBar` 和 `wx.switchTab`，但 2026-06-28 原型明确要求首页/咨询/知识库/我的/存根都不显示底部四项导航。
- **修复方向**：A 先删除 `app.json.tabBar` 并调整 A 页面；B 拉取后调整 profile/consultations。任务 A-T9N，优先级提升为 P0 导航前置任务。

### 🟡 断点 6：scheduler 路由优先级与直觉不完全一致

- **现象**：`agents/scheduler.py` 里 `mode == "image"` 是第一优先级，早于 DTC 正则和所有关键词。
- **后果**：如果前端以图片模式发送文本或图片标签里带 `P0300`，后端仍会优先路由到 `part`，不会进入 `dtc`。这不是 bug，但必须写进联调和测试用例，否则会误判为 DTC 路由失败。
- **修复方向**：保持现状也可以，但测试用例要明确：文字 DTC 用 `mode=text`；图片识别用 `mode=image`。

### 🟠 新风险 7：A 删除 tabBar、B 注册新页面会同时修改 `app.json`

- **现象**：后端 `app.py` 已经预留 `user_bp` 自动注册，B 新增 `routes/user.py` 不需要再改 `app.py`。剩下的共享点主要是：B 新增 `pages/login`、`pages/privacy` 时需要改 `app.json` 注册页面。
- **后果**：A 同时改主业务入口或导航时，两个分支容易在同一文件产生冲突。
- **修复方向**：先合本文档；A 先提交只删除 tabBar 的小变更；B rebase 后只追加 login/privacy/consultations 页面路径，不重排其它字段。

### 🟠 新风险 9：咨询记录与维修记录仍是进程内/模拟数据

- **现象**：A 的 chat/receipt 能生成当前会话数据，但服务重启会丢失；旧 B-U7 允许返回模拟维修列表，且没有咨询记录表。
- **后果**：“我的”里的咨询记录和维修记录无法长期保存，也无法按真实用户查询。
- **修复方向**：B 新增 `user_consultations`、`user_repairs` 和 GET/POST 接口；A 提供 `consultation_id/sources/receipt_id`，并在 B 接口合并后做非阻塞保存。历史详情读取快照，不重新执行 Agent/RAG。

### 🟠 新风险 8：`user_id` 从写死值变为登录态后，A/B 必须保持同一语义

- **现象**：A 当前前端写死 `test_user_001`，B 登录会返回真实或模拟 `user_id`。
- **后果**：如果 A 继续写死、B 另存一套用户 ID，咨询记录、车辆上下文、我的页统计会对不上。
- **修复方向**：B 登录后把 `user_id` 存到小程序 storage；A 读取同一个 storage key。storage key、字段名见 [06](./06-并行开发边界与合并规则.md)。
