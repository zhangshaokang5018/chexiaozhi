## 1. 本次需求结论

1. 取消首页、咨询、知识库、我的、维修记录存根页面底部的四项导航 Tab。

## 2. 页面关系

```text
首页 index
  ├ 左上角菜单 → 我的 profile
  ├ 热门咨询/快捷输入 → 咨询 chat
  └ 故障码/知识入口 → 知识库 kb 或详情 detail

我的 profile（无底部 Tab）
  ├ 我的维修记录 → 维修记录存根 receipt（无底部 Tab）
  ├ 车辆管理 → B 的车辆资料功能
  └ 咨询记录 → consultations（无底部 Tab）

咨询 chat（无底部导航，保留对话输入栏）
知识库 kb（无底部导航）
```

导航统一使用普通页面栈：进入子页用 `wx.navigateTo`，返回用 `wx.navigateBack`；需要清栈回首页时才用 `wx.reLaunch`。不得再用 `wx.switchTab`。

## 4. A/B 统一界面规范（强制）

> A、B 虽然分开开发，但用户看到的是同一个小程序。以下规范属于验收条件，不是建议。

### 4.1 公共视觉基线

| 项目 | 统一值/规则 |
|------|-------------|
| 页面背景 | `#0f172a` |
| 顶部导航背景 | `#1e293b`，下边框 `#334155` |
| 卡片背景 | 主卡片 `#1e293b`；内层/输入区域 `#0f172a` |
| 主文字 | `#f1f5f9` 或 `#e2e8f0` |
| 次文字 | `#94a3b8`；弱提示 `#64748b` |
| 主操作蓝 | `#3b82f6`；高亮文字可用 `#60a5fa` |
| 品牌/价格强调 | `#f59e0b` |
| 危险 | `#ef4444`；警告文字 `#fcd34d`；成功 `#10b981` |
| 页面水平留白 | `28rpx`；紧凑列表可用 `20-24rpx` |
| 标准卡片 | `1rpx solid #334155`，圆角 `24rpx`，内边距 `24rpx` |
| 紧凑列表项 | 圆角 `16rpx`，上下内边距 `20-28rpx` |
| 导航栏 | 最小高度 `88rpx`，标题 `34rpx/700`，左右点击区宽度至少 `72rpx` |
| 正文 | `24-26rpx`；辅助文字 `20-22rpx`；区块标题 `28-36rpx/700` |
| 页面状态 | loading、空态、错误态必须使用相同居中布局；错误用红色，空态用次文字色 |

只允许以下业务化差异：用户头像头部可用品牌蓝；维修存根内容区可保留“纸质票据”浅色面板。但页面背景、顶部栏、返回按钮、字号层级和状态样式仍遵守公共规范。

### 4.2 页面壳层

所有页面统一使用：

```text
page(#0f172a)
  → screen(min-height: 100vh)
  → status-bar（若项目继续自绘，则所有页面保持同尺寸）
  → nav-bar（左侧菜单/返回、中间“车小智”、右侧仅放真实操作）
  → content/scroll-view
```

- 首页左侧是菜单图标；其它二级页面左侧是返回箭头。
- 标题统一为“车小智”，页面业务标题放在内容区，不允许 A/B 各写一套导航标题尺寸。
- 没有右侧操作时保留等宽占位，保证标题视觉居中。
- 所有页面都不显示底部四项 Tab；chat 的输入栏是业务控件，不属于导航。
- 内容必须避开顶部安全区和底部 `safe-area-inset-bottom`，不可被固定输入栏遮挡。

### 4.3 组件一致性

- 卡片、统计块、菜单行、知识库条目使用同一边框色和字体层级。
- 主按钮统一蓝色或品牌橙色，同一页面只能有一个主要操作；禁用态使用 `#475569/#94a3b8`。
- 菜单行统一“左图标 + 文案 + 右箭头”，高度、分隔线、左右内边距一致。
- 风险信息沿用 A 的语义颜色：普通 `kv`、黄色 `warn`、红色 `danger`、绿色 `good`。
- 不允许 B 为 profile/consultations 引入另一套浅色主题、不同圆角体系或独立字体；A 也不得为 receipt/detail 改掉公共页面壳层。
- 页面文案统一使用中文全角标点；金额统一 `¥4.8k` 或 `¥680`，同一页面不得混用多种格式。

### 4.4 样式文件归属与合并方式

1. `app.less` 是共享视觉基线，A 先用单独小提交清理已废弃 `.tabbar*` 并冻结公共类；B 不在功能分支修改 `app.less`。
2. B 的 profile/login/privacy/consultations 只在各自页面 `.less` 中写业务布局，并复用 `.screen/.status-bar/.nav-bar/.content/.card`。
3. A 的 index/chat/kb/detail/receipt 只修改 A 独占页面样式。
4. 若 B 发现公共类不足，先在文档/群里提出，由 A 做独立公共样式提交；B 拉取后再继续，禁止双方复制出两个近似公共类。
5. 禁止整文件格式化 `app.less/app.json`，避免无意义冲突。

### 4.5 视觉验收

- 从首页进入“我的”、咨询记录、维修存根时，背景、导航高度、标题、返回按钮和卡片边框看起来属于同一产品。
- 以 375px 宽度和常见全面屏高度检查：文字不截断、按钮不溢出、固定输入栏不遮挡最后一条内容。
- A/B 各自提交截图：首页/咨询/知识库由 A 提供；我的/咨询记录由 B 提供；维修存根由 A 提供。最终并排检查后才能完成 UI 验收。

## 5. 咨询记录数据链路

```text
chat 页面 POST /api/chat
  → A scheduler 分发 agent
  → agent 调用 RAG/知识库
  → A 返回结构化结论 + sources
  → chat 正常展示
  → 非阻塞调用 B 的 POST /api/user/consultations 保存快照
  → 我的 → 咨询记录 → GET /api/user/consultations
```

要求：历史记录保存当时的回答快照，不在打开历史记录时重新执行智能体或 RAG。这样知识库后续更新也不会改变旧结论。保存失败不得影响当前聊天展示。

A 的 `/api/chat` 在现有响应上新增可选字段：

```json
{
  "consultation_id": "c_20260628_xxx",
  "sources": [
    { "kind": "dtc", "item_id": "P0300", "title": "发动机缺火（随机/多缸）" }
  ]
}
```

B 保存接口使用 A 返回的 `consultation_id` 做幂等键，避免重复写入。

## 6. 维修记录数据链路

```text
A 智能体命中 → receipt_item 沉淀 → POST /api/receipt 生成维修存根
  → receipt 页面展示
  → 非阻塞调用 B 的 POST /api/user/repairs 保存快照
  → 我的 → 我的维修记录 → receipt 页面读取用户维修记录
```

A 的 `/api/receipt` 需要新增稳定 `receipt_id`；B 使用该值做幂等键。B 的记录接口不可反向依赖 A 的进程内 `_STORE`，否则服务重启后历史会丢失。

## 7. 合并顺序

1. 先合并本次文档更新，A/B 都拉取并变基到同一文档版本。
2. A 先提交 `app.json` 去除 `tabBar` 的小变更。
3. B 拉取后开发 profile、consultations、MySQL 两张记录表和 `/api/user/*` 记录接口。
4. A 并行开发自己的页面导航、`sources/consultation_id/receipt_id`，不修改 B 文件。
5. B 的 `utils/user-api.ts` 和记录接口合并后，A 在自己的 chat/receipt 页面接入非阻塞保存。
6. 最后联调：首页菜单 → 我的 → 咨询记录/我的维修记录，以及 chat → agent → RAG → 保存 → 历史展示。
