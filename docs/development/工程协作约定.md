# 工程协作约定（A/B 并行开发必读）

> 目标：让 A、B 两人能各自独立开发、独立提交，**合并时几乎不产生冲突**。
> 本约定配合 `A-开发与自测指南.md` / `B-开发与自测指南.md` 使用。

---

## 1. 核心原则：一人一文件，不碰公共入口

Git 冲突只发生在"两个人改了同一个文件的同一片区域"。所以约定的本质就一句话：

> **每个功能尽量落在各自独立的文件里；公共入口文件冻结，谁都不改。**

为此后端已经用 **Flask 蓝图(Blueprint)** 拆好了，`app.py` 已冻结。

---

## 2. 文件归属表（谁能改哪些文件）

### 后端 `car-server/`

| 文件 / 目录 | 归属 | 说明 |
| --- | --- | --- |
| `app.py` | 🔒 冻结 | 已注册全部蓝图，**A/B 都不要改**。需要新增整组接口才动，且需两人知会。 |
| `routes/health.py` | 公共 | `/api/ping`，基本不动 |
| `routes/chat.py` | **A** | `/api/chat` |
| `agents/scheduler.py`、`symptom.py`、`dtc.py`、`part.py` | **A** | A 新建 |
| `routes/context.py`、`routes/receipt.py`、`routes/kb.py` | **B** | B 的接口 |
| `agents/maintain.py` | **B** | 报价审核 Agent |
| `services/context.py`、`services/receipt.py` | **B** | B 新建 |
| `knowledge/*.json` | **B 独家** | A **只读不改不提交**（见第 4 节） |
| `requirements.txt` | 共享 | 追加式修改，见第 5 节 |

### 前端 `car-miniapp/`

| 文件 / 目录 | 归属 | 说明 |
| --- | --- | --- |
| `miniprogram/pages/chat/**` | **A** | 聊天页全部 |
| `miniprogram/utils/request.ts` | **A** | 请求封装 |

> 前端基本只有 A 在动，B 不碰前端，所以前端几乎不会冲突。

## 3. 分支策略

```text
main                         # 稳定主干，只接受合并
codex/feature-a-agent-chat   # A 的工作分支
codex/feature-b-kb-receipt   # B 的工作分支
codex/integration-mvp        # 联调集成分支
```

规则：

- A 只在 `codex/feature-a-agent-chat` 上提交，B 只在 `codex/feature-b-kb-receipt` 上提交。
- **开发期间各自提交各自分支，互不影响、绝不冲突。**
- 自测通过后，两人分支都合并到 `codex/integration-mvp` 做联调；联调没问题再并入 `main`。

创建分支：

```bash
git checkout main && git pull
git checkout -b codex/feature-a-agent-chat   # A
# 或
git checkout -b codex/feature-b-kb-receipt   # B
```

---

## 4. 知识库归属（最容易冲突，重点看）

`knowledge/kb_dtc.json`、`kb_cost.json`、`kb_symptom.json` 已经放好起步数据。

- **B 是唯一可以修改和提交知识库的人**（B 是数据权威）。
- **A 只读**：A 的 `symptom/dtc` Agent 直接读这些文件即可，起步数据已够 A 自测。
- A **不要**修改或 `git add` 任何 `knowledge/` 文件。若 A 临时想加数据自测，请口头告诉 B，由 B 加并提交。
- 字段 Schema 已冻结（见总文档第 8 节）：开发期只允许**新增字段**，不许删除/改名。

这样知识库永远只有一个写入者，不会出现"A 的样例和 B 的正式数据撞车"。

---

## 5. 少数共享文件的处理规则

有两个文件双方偶尔都要动，按下面规则可把冲突降到最低、且很好解决：

### `requirements.txt`
- **追加式**：新增依赖加在文件末尾，不要重排已有行。
- 万一合并冲突：两边的依赖取**并集**即可（保留双方新增的行），删掉重复。

### `car-miniapp/miniprogram/app.json` 的 `pages` 数组
- 几乎只有 A 动。若 B 也要加页面，**各自把新页面追加到数组末尾**。
- 冲突时保留双方新增的页面路径即可。

### `app.py`（原则上冻结）
- 蓝图已全部注册，正常开发**不需要**改它。
- 万一要加一整组新接口（新蓝图），由改动方在群里知会另一人后再加注册行，避免同时改。

## 6. 日常提交流程

```bash
# 1. 开工前先同步主干（避免落后太多）
git checkout main && git pull
git checkout codex/feature-a-agent-chat   # 切回自己的分支
git merge main                            # 把主干最新合进来（可选，定期做）

# 2. 开发 + 自测（按各自的「开发与自测指南」打勾）

# 3. 提交自己的分支
git add <你负责的文件>      # 只 add 自己归属的文件
git commit -m "feat(a): 实现调度 Agent 与 steps 展示"
git push origin codex/feature-a-agent-chat
```

提交信息建议带前缀：A 用 `feat(a):`，B 用 `feat(b):`，方便区分。

---

## 7. 进入联调的前置条件（来自总文档 10.0.6）

- A 的自测报告结论为"通过"。
- B 的自测报告结论为"通过"。
- 双方接口 Schema 已冻结。
- 两人分支都合并到 `codex/integration-mvp`。

合并到集成分支时若 `app.py` / `requirements.txt` 出现冲突，按第 5 节规则解决即可——因为路由都在各自的蓝图文件里，冲突会非常小。

---

## 8. 一句话总结

> 改自己的文件、在自己的分支、知识库只让 B 写、app.py 不要碰。做到这四点，开发期零冲突，联调期只剩极少量好解决的小冲突。
