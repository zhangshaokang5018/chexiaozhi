## 这套文档解决什么问题

项目后续仍由两位开发者并行开发，但分工已重新调整：
- **A** 负责现有所有业务主链路：小程序首页/咨询/知识库/维修存根、`/api/chat`、智能体接入、RAG/知识库复用、上下文与维修记录闭环。
- **B** 负责新增用户体系：登录、用户资料、隐私/私人信息、我的页个人数据、用户车辆/偏好/统计等与账号强相关的能力。

两人各自完成了自己的部分并能单独自测，但**合并后链路并没有真正打通**。本套文档基于对**真实代码**的逐行核对，说明：

1. 产品到底要做成什么样（需求与四界面功能点）
2. 数据应该怎么流（前端点击 → 后端 → 智能体 → RAG → 知识库 → 返回）
3. 接口真实长什么样（请求/响应契约，单一事实来源）
4. **现在实际走到了哪一步**，以及 A、B 合并后存在的**断点**
5. 接下来按什么顺序做（合并后的统一任务清单）

## 关键约定（务必遵守）

- **本目录文档为准**：任何接口字段、流程描述若与代码不符，以代码为准并立即回写本文档；不要再新建零散文档。
- **接口契约冻结点**：见 [03](./03-接口契约.md)。前后端任一方要改字段，必须先改 03 文档并通知对方。
- **增量需求优先级**：07 是 2026-06-28 新需求；与 01~06 的旧描述冲突时，以 07 和已同步修订的 03/05/06 为准。
- **代码归属**（新约定，避免冲突）：
  - A 独家：现有主业务链路文件，包括 `routes/chat.py`、`routes/kb.py`、`routes/context.py`、`routes/receipt.py`、`routes/asr.py`、`agents/`、`services/rag.py`、`services/context.py`、`services/receipt.py`、`knowledge/`、`pages/index|chat|kb|receipt|detail`。

  - 共享/需协调：`app.py`、`app.json`、`utils/request.ts`、`requirements.txt`、`.env.example`。除非 [06](./06-并行开发边界与合并规则.md) 明确允许，A/B 不在各自分支里同时改这些文件（`app.py` 已自动注册并容错、`.env.example` 的 `DB_*` 已预留，正常无需再改）。
