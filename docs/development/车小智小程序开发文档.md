# 车小智小程序开发文档

## 1. 文档目标

本文档用于指导「车小智：基于多 Agent 协同的汽车售后商机挖掘与车况决策助手」小程序 MVP 开发。

开发依据：

- 产品说明 PDF：`车小智：基于多Agent协同的汽车售后商机挖掘与车况决策助手.pdf`
- 产品原型图：`docs/prototype/chexiaozhi-miniapp-visual-prototype.png`
- 参考 Demo：聊天式小程序界面、Agent 调度、知识库、维修记录存根

核心原则：

- 先搭最小基座，再做功能。
- 先跑通前后端最简单联通，再接 Agent、知识库和记录闭环。
- A/B 两个角色按功能拆分，不按前端/后端拆分。
- A/B 两个人开发时必须能各自独立开发、独立启动、独立测试，避免互相等待。
- 联合调试放到最后，只有双方功能自测通过后才进入联调。
- 每个功能开发完成时必须同步输出测试文档，AI 按测试文档自动测试。
- MVP 优先保证链路完整、数据结构清晰、演示稳定，不追求大而全。

## 2. 产品范围

### 2.1 MVP 要做

MVP 只做 1 条完整主链路：

用户输入车况问题 → 调度 Agent 判断意图 → 专业 Agent 处理 → 检索最小知识库 → 输出诊断建议 → 生成维修记录存根。

MVP 支持 4 类输入：

- 文字/语音转文字症状描述，例如“发动机咕噜咕噜响”
- 故障码查询，例如“P0300 是什么意思”
- 图片识别模拟，例如“拍刹车片 / 拍机油报警 / 拍报价单”
- 报价审核，例如“4S 店报价 800 元换机油机滤合理吗”

MVP 支持 4 类 Agent：

- 调度 Agent：意图识别与任务分发
- 症状分析 Agent：异响、抖动、报警、过热等症状判断
- 故障码解读 Agent：DTC 代码解释
- 保养建议 Agent：报价审核、费用区间、避坑建议
- 零件识别 Agent：图片输入后的零件/仪表/报价单识别模拟

MVP 支持 3 类知识库：

- 故障码知识库
- 维修成本知识库
- 症状关联知识库

MVP 支持 1 个闭环：

- 维修记录存根 / 核销单

### 2.2 MVP 暂不做

- 真实图像识别模型
- 真实语音识别模型
- 真实 VIN 解析
- 真实维修店推荐
- 真实配件供应链接入
- 支付、下单、预约
- 车企换车商机分发
- 后台管理系统

这些能力可以在 V1.5 / V2.0 中扩展。

## 3. 最小基座搭建

基座阶段的目标不是完成业务，而是保证小程序和服务端能最小联通。

### 3.1 基座目标

必须先完成：

1. 小程序项目能启动。
2. 服务端项目能启动。
3. 小程序能请求服务端 `/api/ping`。
4. 服务端能返回固定 JSON。
5. 小程序能把返回结果展示在页面上。
6. 本地开发环境文档写清楚启动方式。

只有基座跑通后，才能进入 Agent、知识库、核销单等功能开发。

### 3.1.1 AI 技术选型

本项目知识库采用 RAG，智能体编排采用 LangChain / LangGraph。

推荐优先使用阿里云百炼作为国内统一模型供应商。原因：

- 一个供应商可覆盖 LLM、Embedding、Rerank。
- 百炼支持 LangChain 集成。
- 百炼提供 OpenAI 兼容接口，后续替换模型成本低。
- API Key 管理相对简单，MVP 阶段尽量只需要一个 `DASHSCOPE_API_KEY`。

推荐组合：

| 模块 | 技术选择 | 说明 |
| --- | --- | --- |
| LLM | 阿里云百炼 Qwen 系列 | 用于生成诊断回答、澄清问题、门店沟通话术 |
| RAG 框架 | LangChain | 用于文档切分、向量化、Retriever、Prompt 拼装 |
| Agent 编排 | LangGraph | 用于调度 Agent、症状 Agent、DTC Agent、报价 Agent、零件 Agent 的状态流转 |
| Embedding | 百炼 `text-embedding-v4` | 用于维修手册、故障码、症状、成本知识向量化 |
| Rerank | 百炼 `qwen3-rerank` | 用于召回后重排，提高 RAG 命中准确率 |
| 向量库 MVP | FAISS 或 Chroma 本地库 | 最快落地，不依赖额外云资源 |
| 向量库后续 | 阿里云向量检索 / Elasticsearch / AnalyticDB 向量能力 | 数据量变大后再切换 |

LangChain 与 LangGraph 使用边界：

- LangChain：负责 RAG、Prompt、模型调用、输出解析。
- LangGraph：负责多 Agent 流程编排、状态机、条件分支、失败回退。

MVP 可以先用 LangChain 跑通 RAG；当调度逻辑稳定后，再把 Agent 流程迁入 LangGraph。若时间紧，第一版也可以直接用 LangGraph 建一个简单状态图。

需要配置的环境变量：

```bash
DASHSCOPE_API_KEY=阿里云百炼APIKey
BAILIAN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen-plus
EMBEDDING_MODEL=text-embedding-v4
RERANK_MODEL=qwen3-rerank
```

说明：

- `DASHSCOPE_API_KEY` 是必须项。
- `BAILIAN_BASE_URL` 根据实际地域和百炼控制台返回的 API Host 调整。
- 如果使用百炼 OpenAI 兼容接口，可在代码中把 `api_key` 指向 `DASHSCOPE_API_KEY`。
- MVP 不需要阿里云 AccessKey/SecretKey，除非后续接 OSS、云数据库、云搜索或其他阿里云资源。

备选方案：

| 供应商 | 适用场景 | 需要的 Key |
| --- | --- | --- |
| 火山引擎方舟 | 偏向豆包模型、OpenAI 兼容迁移、火山生态部署 | 方舟 API Key |
| MiniMax | 偏向长文本、对话和多模态能力探索 | `MINIMAX_API_KEY` + `MINIMAX_GROUP_ID` |
| 硅基流动 | 偏向多模型聚合、快速试用不同开源/闭源模型 | SiliconFlow API Key |

本项目建议不要一开始混用多个供应商，否则联调、计费、模型效果排查都会变慢。MVP 统一用百炼即可。

### 3.3 基座接口

#### GET `/api/ping`

用途：验证小程序与服务端联通。

返回：

```json
{
  "ok": true,
  "name": "chexiaozhi-server",
  "version": "0.1.0"
}
```

验收：

- 小程序页面显示 `服务已连接`
- 控制台无跨域或网络错误
- 服务端日志能看到请求

### 3.4 基座分工

基座阶段不分 A/B 功能角色，先共同完成最小联通。

| 事项 | 负责人 | 产物 |
| --- | --- | --- |
| 小程序页面骨架 | A | `pages/chat` 可打开 |
| 服务端启动骨架 | B | Flask 服务可启动 |
| 请求封装 | A | `utils/request.ts` |
| `/api/ping` 接口 | B | 固定 JSON 返回 |
| 联调 | A + B | 小程序显示服务已连接 |
| 启动说明 | A + B | `README.md` |

基座完成后，再按功能进入 A/B 分工。

## 4. A/B 功能分工

注意：A/B 不按前端和后端拆，而是按产品功能链路拆。每个角色都要对自己负责的功能从界面、接口、数据到验收完整负责。

A/B 并行开发要求：

- 每个人维护自己的功能分支或独立工作目录。
- 每个人的功能必须提供 mock 数据或本地 stub，不能依赖对方功能才能启动。
- 每个人必须能用自己的测试文档独立完成 AI 自动测试。
- 双方约定稳定接口 Schema，开发期间只允许兼容性新增字段，不随意删除或改名。
- 双方共同使用 `car-miniapp/miniprogram/pages/chat` 作为小程序界面基座，不另起页面重复实现聊天界面。
- A 可以替换 mock 调用为真实 `/api/chat`，但不随意修改 WXML 结构和 CSS 类名。
- B 只按约定 JSON Schema 返回数据，不直接改聊天界面结构。
- 联调前必须提交：功能说明、接口说明、测试文档、AI 测试结果。

推荐分支：

```text
codex/feature-a-agent-chat
codex/feature-b-kb-receipt
codex/integration-mvp
```

推荐本地调试方式：

| 角色 | 独立调试方式 | 不能依赖 |
| --- | --- | --- |
| A | 使用 `pages/chat` 内置 mock 回复，后续替换为真实 `/api/chat` | 不依赖 B 的真实知识库 |
| B | 使用 curl / Postman / pytest 调接口，先完成知识库、报价审核、receipt 数据 | 不依赖 A 的小程序页面 |

联调只在 `codex/integration-mvp` 或约定集成分支进行。

### 4.1 角色 A：车况诊断与 Agent 对话链路

角色 A 负责用户从输入问题到获得诊断结果的主链路。

负责范围：

- 聊天主界面
- 用户输入
- 快捷问题
- 调度 Agent 展示
- 诊断步骤展示
- 症状分析
- 故障码解读
- 零件识别模拟
- Agent 回复卡片
- 法律免责声明展示

角色 A 的核心目标：

让用户能在小程序里问一个车况问题，并看到结构化诊断结果。

角色 A 独立调试要求：

- 基于 `car-miniapp/miniprogram/pages/chat` 开发，不新建第二套聊天界面。
- 保留页面中的消息结构、Agent chip、steps、blocks、price、legal_note、车辆信息弹窗、维修记录弹窗。
- 可以把内置 mock 逐步替换为真实 `/api/chat` 返回。
- 页面在没有真实服务端时仍能用 mock 数据预览。
- A 的自测不依赖 B 的知识库和核销单真实逻辑。

### 4.2 角色 B：知识库、报价审核与维修记录闭环

角色 B 负责数据支撑和闭环沉淀。

负责范围：

- 知识库 JSON 结构
- 维修成本基准
- 报价审核逻辑
- 用户车辆上下文
- VIN 脱敏
- 维修记录存根
- 核销单弹窗
- 历史记录数据结构
- 后续成本画像预留字段

角色 B 的核心目标：

让诊断结果能引用知识库、给出价格区间，并沉淀成维修记录。

角色 B 独立调试要求：

- 提供本地接口启动脚本。
- 提供 curl 或 pytest 测试脚本。
- 提供固定 user_id 的测试数据。
- B 的自测不依赖 A 的小程序页面。
- B 需要保证接口返回字段与约定 Schema 一致。

## 7. Agent 路由规则

### 7.1 调度 Agent

输入：

- text
- mode
- image_label

输出：

- agent
- intent
- confidence

路由规则：

| 条件 | 目标 Agent | 意图 |
| --- | --- | --- |
| `mode=image` | part | 图像识别/零件匹配 |
| 包含 P/B/C + 4 位数字 | dtc | 故障码解读 |
| 包含“报价、费用、价格、多少钱、合理、贵、保养” | maintain | 保养建议/报价审核 |
| 包含“响、抖、顿挫、报警、灯亮、水温、机油、刹车、转向”等 | symptom | 症状分析 |
| 无匹配 | scheduler | 综合咨询/需补充信息 |

### 7.2 症状分析 Agent

输入：

- text
- context

逻辑：

- 从症状知识库匹配关键词。
- 取最高匹配项。
- 输出故障点、紧急程度、应急处理、避坑建议和费用区间。

### 7.3 故障码解读 Agent

输入：

- text
- context

逻辑：

- 提取 DTC 代码。
- 查询故障码知识库。
- 输出描述、可能原因、修复难度、建议排查顺序和费用区间。

### 7.4 保养建议 Agent

输入：

- text
- context

逻辑：

- 匹配维修项目。
- 查询成本基准。
- 如果用户输入了报价，判断是否低于或高于合理区间。
- 输出报价审核、价格区间和避坑三件套。

### 7.5 零件识别 Agent

输入：

- image_label
- context

逻辑：

- MVP 阶段使用预设图片识别结果。

### 10.0.3 AI 自动测试要求

每个功能完成后，AI 必须根据测试文档执行自动测试。

AI 自动测试可以使用：

- 单元测试：pytest
- 接口测试：curl / pytest requests
- 页面静态检查：读取 WXML / WXSS / TS
- 页面视觉检查：浏览器截图或微信开发者工具截图
- Mock 数据测试：使用固定 JSON 验证页面渲染

AI 测试报告必须包含：

- 测试时间
- 测试命令
- 通过用例
- 失败用例
- 失败原因
- 修复建议
- 是否允许进入联调

## 11. 合规与安全要求

- 所有 AI 建议必须展示“仅供参考，请以当地授权维修点为准”。
- 高风险症状必须提示立即停车或线下检查。
- VIN 展示默认脱敏。
- 知识库未命中时，不允许编造结论。
- 报价建议只给参考区间，不做强制交易建议。
- 维修记录存根 MVP 阶段必须标注为模拟。
