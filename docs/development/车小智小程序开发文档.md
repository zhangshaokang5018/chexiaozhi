# 车小智小程序开发文档

## 1. 文档目标

本文档用于指导「车小智：基于多 Agent 协同的汽车售后商机挖掘与车况决策助手」小程序 MVP 开发。

开发依据：

- 产品说明 PDF：`车小智：基于多Agent协同的汽车售后商机挖掘与车况决策助手.pdf`
- 产品原型图：`docs/prototype/chexiaozhi-miniapp-visual-prototype.png`
- 参考 Demo：聊天式小程序界面、Agent 调度、知识库、维修记录存根

核心原则：

- 先搭最小基座，再做功能。
- 先跑通前后端最简单联通，再接 Agent、知识库和记录闭环。
- A/B 两个角色按功能拆分，不按前端/后端拆分。
- A/B 两个人开发时必须能各自独立开发、独立启动、独立测试，避免互相等待。
- 联合调试放到最后，只有双方功能自测通过后才进入联调。
- 每个功能开发完成时必须同步输出测试文档，AI 按测试文档自动测试。
- MVP 优先保证链路完整、数据结构清晰、演示稳定，不追求大而全。

## 2. 产品范围

### 2.1 MVP 要做

MVP 只做 1 条完整主链路：

用户输入车况问题 → 调度 Agent 判断意图 → 专业 Agent 处理 → 检索最小知识库 → 输出诊断建议 → 生成维修记录存根。

MVP 支持 4 类输入：

- 文字/语音转文字症状描述，例如“发动机咕噜咕噜响”
- 故障码查询，例如“P0300 是什么意思”
- 图片识别模拟，例如“拍刹车片 / 拍机油报警 / 拍报价单”
- 报价审核，例如“4S 店报价 800 元换机油机滤合理吗”

MVP 支持 4 类 Agent：

- 调度 Agent：意图识别与任务分发
- 症状分析 Agent：异响、抖动、报警、过热等症状判断
- 故障码解读 Agent：DTC 代码解释
- 保养建议 Agent：报价审核、费用区间、避坑建议
- 零件识别 Agent：图片输入后的零件/仪表/报价单识别模拟

MVP 支持 3 类知识库：

- 故障码知识库
- 维修成本知识库
- 症状关联知识库

MVP 支持 1 个闭环：

- 维修记录存根 / 核销单

MVP 必须补齐的产品能力：

- 知识库页支持搜索：故障码、成本、症状三个分类都必须能按关键词搜索。
- 知识库页支持筛选：故障码按系统/级别筛选，成本按车型/项目/价格筛选，症状按部位/紧急程度筛选。
- 知识库详情页支持三类内容：故障码详情、成本详情、症状详情。
- 知识库条目支持“一键咨询 Agent”，把当前条目的 code、item 或 symptom 带入聊天页。
- 知识库搜索无结果时不能空白，必须提示用户改关键词或直接咨询 Agent。
- 用户中心支持维修记录历史列表，可进入单条维修记录详情。
- 车辆信息支持编辑，至少包含车型、能源类型、里程、城市、VIN。
- 高风险症状必须触发强提醒，例如刹车失灵、机油报警灯、水温过高、电池高压故障。
- Agent 回复后支持用户反馈：“有帮助 / 不准确”，用于后续数据闭环。
- 报价单识别结果必须结构化展示：维修项目、店家报价、市场参考价、是否偏高、建议行动。

### 2.2 MVP 暂不做

- 真实图像识别模型
- 真实语音识别模型
- 真实 VIN 解析
- 真实维修店推荐
- 真实配件供应链接入
- 支付、下单、预约
- 车企换车商机分发
- 后台管理系统

这些能力可以在 V1.5 / V2.0 中扩展。

### 2.3 V1.0 增强项

这些功能建议在 MVP 主链路稳定后加入，不阻塞第一轮演示，但开发时要预留入口和数据结构：

- 首页统一搜索/提问入口：输入故障码、症状、报价问题后自动进入知识库结果或聊天页。
- 常见问题 FAQ：覆盖机油、刹车、异响、故障灯、电瓶、轮胎等高频问题。
- 知识来源展示：Agent 回复和知识库详情展示“来源：故障码库 / 成本基准库 / 症状库”。
- 诊断报告页：把一次聊天诊断沉淀为报告，包含问题、可能原因、建议检查顺序、费用区间、风险等级。
- 历史记录继续追问：从历史记录详情页带着上下文回到聊天页继续问。
- 成本对比说明：展示原厂件、副厂件、工时费、地区差异导致的价格变化。

### 2.4 V1.5 / V2.0 排期项

这些属于产品成长阶段或生态阶段，不进入当前 MVP 的完成标准：

- 真实语音输入：接入阿里云智能语音交互 / 百炼语音能力。
- 真实图片识别：接入阿里云视觉智能开放平台 / 百炼多模态能力。
- 用户维修案例反馈：用户提交最终维修项目、价格、门店、结果，形成案例数据库。
- 附近透明维修店：基于服务评价和价格透明度推荐维修点。
- 换车/购车商机判断：当维修成本持续偏高时，提示换车决策或购车参考。
- 维修工工作台：服务维修工的语音实时转单、诊断报告、模型校对能力。

## 3. 最小基座搭建

基座阶段的目标不是完成业务，而是保证小程序和服务端能最小联通。

### 3.1 基座目标

必须先完成：

1. 小程序项目能启动。
2. 服务端项目能启动。
3. 小程序能请求服务端 `/api/ping`。
4. 服务端能返回固定 JSON。
5. 小程序能把返回结果展示在页面上。
6. 本地开发环境文档写清楚启动方式。

只有基座跑通后，才能进入 Agent、知识库、核销单等功能开发。

### 3.1.1 AI 技术选型

本项目知识库采用 RAG，智能体编排采用 LangChain / LangGraph。

本项目统一使用阿里云百炼 / 阿里云体系作为国内模型与 AI 能力供应商。所有 AI 能力优先使用阿里云侧的 Key，不再混用火山、MiniMax、硅基流动等其他供应商，避免多 Key、多计费、多模型效果排查带来的协作成本。

统一供应商原则：

- 对话大模型用阿里云百炼 Qwen 系列。
- Embedding 用阿里云百炼 Embedding。
- Rerank 用阿里云百炼 Rerank。
- RAG 检索链路用阿里云百炼模型能力。
- 语音识别优先用阿里云智能语音交互 / 百炼支持的语音能力。
- 图片识别优先用阿里云视觉智能开放平台 / 百炼支持的多模态视觉能力。
- 开发文档、代码示例、环境变量统一按阿里云 Key 设计。

推荐组合：

| 模块 | 技术选择 | 说明 |
| --- | --- | --- |
| LLM | 阿里云百炼 Qwen 系列 | 用于生成诊断回答、澄清问题、门店沟通话术 |
| RAG 框架 | LangChain | 用于文档切分、向量化、Retriever、Prompt 拼装 |
| Agent 编排 | LangGraph | 用于调度 Agent、症状 Agent、DTC Agent、报价 Agent、零件 Agent 的状态流转 |
| Embedding | 百炼 `text-embedding-v4` | 用于维修手册、故障码、症状、成本知识向量化 |
| Rerank | 百炼 `qwen3-rerank` | 用于召回后重排，提高 RAG 命中准确率 |
| 语音识别 | 阿里云智能语音交互 / 百炼语音能力 | 用于把车主语音描述转成文字，再进入调度 Agent |
| 图片识别 | 阿里云视觉智能开放平台 / 百炼多模态视觉能力 | 用于仪表盘报警灯、零件、维修报价单识别 |
| 向量库 MVP | FAISS 或 Chroma 本地库 | 最快落地，不依赖额外云资源 |
| 向量库后续 | 阿里云向量检索 / Elasticsearch / AnalyticDB 向量能力 | 数据量变大后再切换 |

LangChain 与 LangGraph 使用边界：

- LangChain：负责 RAG、Prompt、模型调用、输出解析。
- LangGraph：负责多 Agent 流程编排、状态机、条件分支、失败回退。

MVP 可以先用 LangChain 跑通 RAG；当调度逻辑稳定后，再把 Agent 流程迁入 LangGraph。若时间紧，第一版也可以直接用 LangGraph 建一个简单状态图。

需要配置的环境变量：

```bash
DASHSCOPE_API_KEY=阿里云百炼APIKey
BAILIAN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen-plus
EMBEDDING_MODEL=text-embedding-v4
RERANK_MODEL=qwen3-rerank
ALIYUN_AUDIO_APP_KEY=阿里云智能语音应用AppKey
ALIYUN_ACCESS_KEY_ID=阿里云AccessKeyId
ALIYUN_ACCESS_KEY_SECRET=阿里云AccessKeySecret
ALIYUN_VISION_REGION=cn-shanghai
```

说明：

- `DASHSCOPE_API_KEY` 是对话大模型、Embedding、Rerank、RAG 链路的必须项。
- `BAILIAN_BASE_URL` 根据实际地域和百炼控制台返回的 API Host 调整。
- 如果使用百炼 OpenAI 兼容接口，可在代码中把 `api_key` 指向 `DASHSCOPE_API_KEY`。
- 语音识别如果使用阿里云智能语音交互，需要 `ALIYUN_AUDIO_APP_KEY`，以及阿里云 AccessKey。
- 图片识别如果使用阿里云视觉智能开放平台，需要阿里云 AccessKey。
- 如果百炼控制台已提供统一的多模态视觉 / 语音模型 API，则优先走 `DASHSCOPE_API_KEY`，减少额外 Key。
- MVP 阶段如果语音和图片只做模拟，可以先不配置语音和视觉 Key，但代码结构必须预留阿里云接入位。

备选方案：

| 供应商 | 适用场景 | 需要的 Key |
| --- | --- | --- |
| 火山引擎方舟 | 偏向豆包模型、OpenAI 兼容迁移、火山生态部署 | 方舟 API Key |
| MiniMax | 偏向长文本、对话和多模态能力探索 | `MINIMAX_API_KEY` + `MINIMAX_GROUP_ID` |
| 硅基流动 | 偏向多模型聚合、快速试用不同开源/闭源模型 | SiliconFlow API Key |

本项目建议不要一开始混用多个供应商，否则联调、计费、模型效果排查都会变慢。MVP 统一用阿里云百炼 / 阿里云体系即可。

Key 管理要求：

- 所有 Key 只能放在服务端环境变量或服务器密钥管理中。
- 小程序前端严禁写入任何 API Key。
- 仓库只允许提交 `.env.example`，不允许提交真实 `.env`。
- 开发者本地用自己的阿里云测试 Key，联调环境用统一测试 Key。
- 生产环境上线前必须更换为正式环境 Key，并配置调用额度和告警。

### 3.3 基座接口

#### GET `/api/ping`

用途：验证小程序与服务端联通。

返回：

```json
{
  "ok": true,
  "name": "chexiaozhi-server",
  "version": "0.1.0"
}
```

验收：

- 小程序页面显示 `服务已连接`
- 控制台无跨域或网络错误
- 服务端日志能看到请求

### 3.4 基座分工

基座阶段不分 A/B 功能角色，先共同完成最小联通。

| 事项 | 负责人 | 产物 |
| --- | --- | --- |
| 小程序页面骨架 | A | `pages/index`、`pages/chat`、`pages/kb`、`pages/profile`、`pages/receipt`、`pages/detail` 可打开 |
| 服务端启动骨架 | B | Flask 服务可启动 |
| 请求封装 | A | `utils/request.ts` |
| `/api/ping` 接口 | B | 固定 JSON 返回 |

| 启动说明 | A + B | `README.md` |

## 4. A/B 功能分工

> 详细的「逐任务开发清单 + 完成定义(DoD) + 怎么自测」见：
> - 角色 A：`docs/development/A-开发与自测指南.md`
> - 角色 B：`docs/development/B-开发与自测指南.md`
>
> 本节只讲分工原则；具体每步怎么做、做到什么程度算完成、怎么验证，以上面两份指南为准。

注意：A/B 不按前端和后端拆，而是按产品功能链路拆。每个角色都要对自己负责的功能从界面、接口、数据到验收完整负责。

A/B 并行开发要求：

- 每个人维护自己的功能分支或独立工作目录。
- 每个人的功能必须提供 mock 数据或本地 stub，不能依赖对方功能才能启动。
- 每个人必须能用自己的测试文档独立完成 AI 自动测试。
- 双方约定稳定接口 Schema，开发期间只允许兼容性新增字段，不随意删除或改名。
- 双方共同使用已落地的小程序页面基座，不另起页面重复实现界面。
- 页面基座包括：`pages/index` 首页、`pages/chat` 咨询页、`pages/kb` 知识库页、`pages/profile` 我的页、`pages/receipt` 核销单页、`pages/detail` 故障码详情页。
- A 可以替换咨询页 mock 调用为真实 `/api/chat`，但不随意修改公共导航、tabbar、卡片样式和页面结构。
- B 只按约定 JSON Schema 返回数据，主要填充知识库、核销单、车辆档案数据，不直接改咨询页结构。
- 联调前必须提交：功能说明、接口说明、测试文档、AI 测试结果。

### A/B 做完后应该是什么样

为了避免只写“负责范围”但不知道做到哪算完成，A/B 的交付物按下面的样子验收。

| 角色 | 做完后用户/开发者能看到什么 | 自己怎么证明做对了 | 不算完成的情况 |
| --- | --- | --- | --- |
| A | 小程序可以打开首页、进入咨询页、发送问题、看到用户气泡、Agent 回复卡片、诊断步骤、风险提醒、价格提示、免责声明，并能进入故障码详情页 | 按 `docs/testing/A-agent-chat-test-plan.md` 跑完 A-001 到 A-013；没有服务端时也能用 mock 数据完整演示 | 只能看到静态页面；发送后没有结构化回复；页面依赖 B 的接口才能展示；改乱公共导航或页面样式 |
| B | 服务端接口可本地启动；curl/pytest 能请求知识库、上下文、报价审核、维修记录、RAG 检索和 Agent 路由；返回 JSON 字段符合文档 Schema | 按 `docs/testing/B-kb-receipt-test-plan.md` 跑完 B-001 到 B-015；不用打开小程序也能验证全部接口 | 只有函数没有接口；只能人工看返回；返回字段和小程序约定不一致；接口依赖 A 的页面才能测试 |
| 联调 | 小程序真实请求服务端后，症状、故障码、报价、图片模拟、维修记录都能跑通一遍 | 按 `docs/testing/integration-test-plan.md` 跑完 I-001 到 I-009 | A 或 B 任一方没有独立测试通过就开始联调 |

### A 的完成画面

A 做完后，重点看小程序页面：

- 首页功能入口能正常进入咨询页、知识库页、我的页。
- 咨询页顶部有车辆上下文，底部能输入问题和点击快捷问题。
- 输入“P0300”后，页面出现用户消息和故障码 Agent 回复。
- 输入“咕噜咕噜响”后，页面出现症状分析 Agent 回复。
- 输入“800 元换机油合理吗”后，页面出现价格区间和报价判断。
- Agent 回复里必须能看到 Agent 名称、意图、处理步骤、知识库引用/建议块、风险提醒、免责声明。
- 无服务端或网络失败时，页面展示错误提示，而不是空白或卡死。

A 自测时只需要证明“页面和对话链路能独立展示正确结构”。A 不需要证明 RAG 真的检索准确，那是 B 的范围。

### B 的完成结果

B 做完后，重点看接口和数据：

- `/api/ping` 能返回健康状态。
- `/api/chat` 对症状、故障码、报价审核、图片模拟四类输入能路由到正确 Agent。
- `/api/context` 能读取和更新固定测试用户的车辆信息。
- `/api/receipt` 能根据测试用户生成无记录/有记录两种核销单结果。
- `/api/kb/dtc`、`/api/kb/cost`、`/api/kb/symptom` 能返回知识库数据。
- RAG 对已知问题能命中知识块，对无关问题能给澄清或无法判断提示，不编造维修结论。
- LangGraph 或 LangChain 调度链路的每个节点都有可验证日志或测试断言。

B 自测时只需要证明“服务端能力和数据结构是对的”。B 不需要打开小程序证明页面好看，那是 A 和最终联调的范围。

### 最简单的判断口径

- A 问自己：我断网或服务端没启动时，能不能用 mock 在小程序里演示完整诊断流程？
- B 问自己：我不打开小程序，只用 pytest/curl，能不能证明所有接口返回正确？
- 联调时再问：小程序关掉 mock 后，能不能真实调用服务端跑完整流程？

## 4.0 Git 提交与协作规范

本项目多人使用小程序开发工具和 GitHub 协作，提交代码时必须避免把本地无用文件、个人配置、缓存产物提交到仓库，防止其他人拉代码后环境出问题。

所有开发成员提交前必须遵守：

- 只 stage 本次任务相关文件，不使用 `git add -A` 一次性提交全部改动。
- 不提交本地配置、缓存、构建产物、临时文件。
- 不提交 `node_modules`、`dist`、`miniprogram_npm`、`.DS_Store`、日志文件、截图临时文件等。
- 不提交个人环境配置，例如本地 IP、私钥、API Key、微信开发者工具 private 配置。
- 提交前必须执行 `git status --short` 查看文件列表。
- 提交前必须执行 `git diff --stat` 查看改动范围。
- 如果发现和当前任务无关的文件，必须先停止并确认，不允许默默提交。
- 提交时使用显式路径，例如：

```bash
git add -- car-miniapp/miniprogram/pages/chat/chat.wxml \
  car-miniapp/miniprogram/pages/chat/chat.ts \
  car-miniapp/miniprogram/pages/chat/chat.less
```

禁止直接执行：

```bash
git add -A
```

推荐提交流程：

```bash
git status --short
git diff --stat
git add -- <本次任务相关文件>
git status --short
git commit -m "简短描述本次改动"
git push -u origin <当前分支>
```

需要特别注意：

- `project.private.config.json` 通常包含个人微信开发者工具配置，默认不要提交。
- `.env`、`.env.local`、包含 API Key 的配置文件默认不要提交。
- 如果确实需要新增配置模板，提交 `.env.example`，不要提交真实密钥。
- 如果引入新依赖，应提交 `package.json` 和锁文件，但不要提交依赖安装目录。

## 7. Agent 路由规则

### 7.1 调度 Agent

输入：

- text
- mode
- image_label

输出：

- agent
- intent
- confidence

路由规则：

| 条件 | 目标 Agent | 意图 |
| --- | --- | --- |
| `mode=image` | part | 图像识别/零件匹配 |
| 包含 P/B/C + 4 位数字 | dtc | 故障码解读 |
| 包含“报价、费用、价格、多少钱、合理、贵、保养” | maintain | 保养建议/报价审核 |
| 包含“响、抖、顿挫、报警、灯亮、水温、机油、刹车、转向”等 | symptom | 症状分析 |
| 无匹配 | scheduler | 综合咨询/需补充信息 |

### 7.2 症状分析 Agent

输入：

- text
- context

逻辑：

- 从症状知识库匹配关键词。
- 取最高匹配项。
- 输出故障点、紧急程度、应急处理、避坑建议和费用区间。

### 7.3 故障码解读 Agent

输入：

- text
- context

逻辑：

- 提取 DTC 代码。
- 查询故障码知识库。
- 输出描述、可能原因、修复难度、建议排查顺序和费用区间。

### 7.4 保养建议 Agent

输入：

- text
- context

逻辑：

- 匹配维修项目。
- 查询成本基准。
- 如果用户输入了报价，判断是否低于或高于合理区间。
- 输出报价审核、价格区间和避坑三件套。

### 7.5 零件识别 Agent

输入：

- image_label
- context

逻辑：

- MVP 阶段使用预设图片识别结果。
- 输出零件识别结果、零件库匹配、原厂件校验、副厂件建议和避坑建议。

### 8.4 高风险规则

以下场景必须触发强提醒：

- 刹车失灵、刹车踩空、刹车距离明显变长。
- 机油压力报警灯亮、机油灯红灯。
- 水温过高、发动机过热、冷却液大量泄漏。
- 新能源车高压电池报警、绝缘故障、冒烟、焦糊味。
- 行驶中方向失控、严重抖动、轮胎爆胎风险。

强提醒输出要求：

- `risk_level` 必须为 `高`。
- 回复中必须出现强提醒块。
- 建议动作必须明确，例如“立即靠边停车”“不要继续高速行驶”“联系救援或授权维修点”。
- 不允许只给普通维修建议。

### 8.5 用户反馈数据

字段：

```json
{
  "user_id": "openid_xxx",
  "message_id": "msg_001",
  "agent": "dtc",
  "rating": "helpful",
  "comment": "",
  "created_at": "2026-06-27 13:20:00"
}
```

用途：

- 统计 Agent 回复是否有帮助。
- 标记不准确案例，后续进入人工复核或知识库更新。
- 为 V1.5 的案例数据库和数据飞轮预留基础数据。

## 11. 合规与安全要求
