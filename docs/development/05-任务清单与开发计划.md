## A 任务线 — 打通现有主业务（M1 必做）

### A-T1 · 让 `/api/chat` 真正调用智能体
- **问题来源**：04 断点 1
- **涉及文件**：`routes/chat.py`、消费 `agents/maintain.py`（均由 A 负责）
- **做什么**：
  1. `chat()` 在 `route()` 得到 `agent` 后，按 agent 分发到对应智能体的 `handle(text, context)`。
  2. 先接最易接的 `maintain`：命中 `maintain` 时调用 `agents.maintain.handle()`，用其 `reply/steps/hit/confidence` 覆盖 `build_reply()` 占位。
  3. 保持对外响应外形不变（见 [03 §2](./03-接口契约.md)）。注意：由于 `maintain` 当前会返回 `miss/good`，本任务不能假设绝对前端零改动，需配合 A-T2 做契约归一。
  4. 智能体异常时回退占位文案（保持"永远能跑")。
- **验收**：发送"800 换机油机滤合理吗"→ 返回真实价格区间 + 合理性判断 + 避坑 block，`price_range` 非空。
- **依赖**：无（maintain 已就绪）。建议**第一个做**，作为接入范式。

### A-T2 · 统一 chat/maintain 输出契约
- **问题来源**：04 断点 1.5
- **涉及文件**：优先 `routes/chat.py`（后端归一化）；必要时 `utils/request.ts`、`pages/chat/chat.wxml`
- **做什么**：
  1. 在 `chat.py` 消费智能体结果时，统一规范 `steps[].status`：前端不支持的 `miss` 转为 `pending` 或 `todo`，并保留 `detail` 说明未命中。
  2. 统一规范 `blocks[].type`：`good` 转为前端已支持的结构，例如 `type="kv"` + `good=true`，或同步扩展前端类型为 `good` 并补渲染。
  3. 之后新建的 dtc/symptom/part 智能体都按同一规范返回，避免每个 Agent 各写一套。
- **验收**：maintain 命中、maintain 未命中两种响应都能被前端正常渲染；TS 类型与接口文档一致。
- **依赖**：A-T1 可并行，但建议在 A-T1 同一个 PR/提交里完成。

### A-T3 · 新建 dtc 故障码智能体
- **问题来源**：04 断点 2
- **涉及文件**：新建 `agents/dtc.py`；`routes/chat.py` 分发；数据用 `knowledge/kb_dtc.json` + `services/rag.py`
- **做什么**：参照 `maintain.py` 的 `handle()` 契约（见 [03 §9](./03-接口契约.md)），实现：提取 `[PBC]\d{4}` → 精确查 dtc 库 → 命中给 desc/plain/cause/level/价格区间 + 风险等级 block；未命中走 RAG/澄清。
- **验收**：发送"P0300 是什么意思"→ 返回缺火释义、风险等级（level→文本）、价格区间、排查建议。

### A-T4 · 新建 symptom 症状智能体
- **问题来源**：04 断点 2
- **涉及文件**：新建 `agents/symptom.py`；数据用 `kb_symptom.json` + `services/rag.py`
- **做什么**：关键词/RAG 匹配 `keywords` → 命中给 `fault`/`level`(高中低)/`tip`/价格区间；`level=高` 时必须输出 `danger` block（高风险强提醒）。未命中给澄清，不编造。
- **验收**：发送"发动机咕噜咕噜响"→ 返回可能故障、紧急程度、排查建议；"机油灯亮"类 → 出现红色 `danger` 强提醒。
