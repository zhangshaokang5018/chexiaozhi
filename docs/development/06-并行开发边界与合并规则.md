# 06 · 并行开发边界与合并规则

> 本文档专门解决 A、B 分别拉代码开发时的冲突问题。原则是：A 负责现有主业务闭环，B 负责新增用户体系；两人只通过稳定契约交互，不在同一批文件里互相改逻辑。

---

## 1. 总原则

1. **A 主业务线优先保持可运行**：首页、咨询、知识库、智能体、RAG、上下文、维修存根都归 A。
2. **B 用户体系独立开发**：登录、我的页、用户资料、私人信息、隐私设置、用户统计都归 B。
3. **共享文件只做注册，不写业务**：`app.py`、`app.json`、`utils/request.ts` 属于高冲突文件，除非本文件明确允许，否则不要在各自分支里随意改。
4. **交界使用稳定契约**：B 提供 `user_id`；A 提供 `consultation_id`、`sources`、`receipt_id`。A 不处理手机号/token，B 不修改 Agent/RAG。
5. **视觉只有一套**：A/B 都遵守 [07 §4](./07-2026-06-28页面与记录增量变更.md)；公共 `app.less` 串行维护，页面业务样式留在各自独占目录。

## 2. 已提前处理的小冲突点

### 2.1 后端 `app.py`

已做小改动：`app.py` 会用 `importlib.util.find_spec("routes.user")` 检测是否存在 `routes/user.py`，存在则 `from routes.user import user_bp` 并自动注册；不存在则现有服务不受影响。

**结果**：B 开发 `/api/user/*` 时只需要新增 `routes/user.py`，不需要再改 `app.py`。

> ⚠️ **硬约定（B 必须遵守）**：
> 1. `routes/user.py` **必须**导出一个**模块级变量，名字精确为 `user_bp`**，且为 `Blueprint` 实例：
>    ```python
>    from flask import Blueprint
>    user_bp = Blueprint("user", __name__)
>    ```
> 2. `app.py` 现已把这行导入包进 `try/except`：当 `routes/user.py` 存在但导入失败（语法错误、未导出 `user_bp` 等）时，**降级为「不注册 user 蓝图」并打印告警，A 的主业务接口照常启动**，不会被一起带崩。即便如此，B 新增 `routes/user.py` 后仍应**第一时间确认 `python app.py` 能正常启动且 `/api/user/*` 已注册**，避免自己的接口悄悄没生效。

### 2.2 前端 `app.json`

2026-06-28 最新原型取消底部四项 Tab，因此 `app.json` 必须串行修改：

1. A 先做 A-T9N，只删除 `tabBar`，保留/整理 A 已有页面，不注册 B 的新页面。
2. A 提交合并后通知 B。
3. B rebase，再一次性新增 login/privacy/consultations 页面文件和路径；不恢复 `tabBar`，不重排 A 的页面配置。

任何一方都不得在未拉取另一方最新 `app.json` 的情况下直接提交该文件。

### 2.3 用户数据存储 `car-server/data/`（PII，必须忽略）

B 的用户体系如果有本地导出/缓存数据（`car-server/data/users.*` 等），可能包含手机号、openid、session token 等**敏感信息（PII）**。这类文件必须忽略，否则会有两个风险：

1. **隐私泄漏**：用户 PII 被误提交进 git 历史（与 §6「不把手机号/token 明文入库」原则冲突）。
2. **共享冲突**：`data/users.json` 作为运行时可变文件被提交后，A、B、不同环境每次运行都会改它，造成无意义的 diff 与合并冲突。

**已落地**：`car-server/.gitignore` 已加入：

```gitignore
# 用户体系本地数据（PII，不入库；格式由 B 选择）。需样例时单独提供 data/users.example.json
data/
```

> 若 B 需要保留一份"样例数据"供他人跑通，应单独提供 `data/users.example.json`（不含真实 PII）并用 `git add -f` 显式纳入版本控制。

### 2.4 用户体系数据库 MySQL（B 的存储；依赖/配置已隔离，A 不受影响）

B 用户体系的存储选型为 **MySQL（本地）**，库名 `chexiaozhi_user`。为保证「A 不被影响、A/B 提交不冲突」，已做如下隔离与预埋：

| 关注点 | 处理 | 谁负责 |
|--------|------|--------|
| **依赖** | MySQL 依赖只放 B 独占的 `requirements-user.txt`（PyMySQL、python-dotenv），**不写进共享的 `requirements.txt`**。A 不装也能跑全部主业务。 | 已建好 `requirements-user.txt` |
| **连接配置** | `.env.example` 已预留 `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME`（注释态）。B 复制为 `.env` 后使用 `DB_USER=cxz_user`、`DB_PASSWORD=cxz_user_dev_2026`、`DB_NAME=chexiaozhi_user`。root 只用于本地建库/授权。 | 已预埋 |
| **建库建表与初始化数据** | 当前 SQL 已提供 4 张基础表；B-U7/B-U8 增加 `user_repairs`、`user_consultations` 后目标为 6 张表，并补 `user_10001` 演示记录。 | B |
| **启动隔离** | **硬约定：B 的 `services/db.py` 必须惰性连库（首次查询才连接），不能在模块导入时连库。** 否则 MySQL 没起时会随 `app.py` 导入 `user_bp` 一起报错。§2.1 已容错降级为「不注册 user 蓝图」，A 不会被带崩；但 B 自己的接口会整段失效。惰性连接下：MySQL 没起也不影响 A，且 `/api/user/*` 被调用时能返回可恢复数据库错误。 | B |
| **数据隔离** | 用户数据全在 `chexiaozhi_user` 库；A 的内存上下文 / Chroma / knowledge JSON 与之零交集。 | — |

> 一句话：A 完全不碰 MySQL（不装依赖、不配 `DB_*`、代码不连库）；B 的库挂了也只影响 `/api/user/*`。建库步骤见 `car-server/README.md`「用户体系数据库」。

## 4. `user_id` 统一规则

| 项 | 约定 |
|----|------|
| storage key | `cxz_user_id` |
| session key | `cxz_session_token` |
| 游客默认 | 未登录时可降级为 `guest_user_001` 或后端返回的 guest user |
| A 读取方式 | A-T5 后从 storage 读取 `cxz_user_id`，没有则用测试/游客值 |
| B 写入方式 | B-U1 登录成功后写入 `cxz_user_id` 和 `cxz_session_token` |

`user_id` 是身份交界；`consultation_id/sources/receipt_id` 是记录交界。B 不要求 A 消费手机号、openid、session token；A 不直接写 MySQL。`session_token` 只允许在登录成功响应里出现一次，之后由前端存储在 `cxz_session_token`，其它接口不得返回 token 明文。

| 字段 | 产生方 | 消费方 | 用途 |
|------|--------|--------|------|
| `consultation_id` | A `/api/chat` | B `/api/user/consultations` | 咨询记录幂等键 |
| `sources[]` | A Agent/RAG | B 咨询记录快照 | 展示当次知识来源，不重新检索 |
| `receipt_id` | A `/api/receipt` | B `/api/user/repairs` | 维修记录幂等键 |

## 5. 合并顺序建议

1. 先合并 2026-06-28 文档更新，A/B 都拉取。
2. A 先合 A-T9N 的 `app.json` 小提交；B rebase 后再注册新页面。
3. A、B 分别开发自己的独占目录；B 先提供记录 API 和 `utils/user-api.ts`，A 后接非阻塞保存。
4. A-T5 与 B-U1 按 `cxz_user_id` 对齐；A-T11 与 B-U7/B-U8 按三个记录字段对齐。
5. 最后做跨线联调，不在任一人的功能分支里临时修改对方文件。

## 6. 不允许的做法

- B 不直接改 `pages/chat` 来读取登录态；由 A-T5 处理。
- B 不直接改 `services/context.py` 来同步车辆资料；先做 `services/user.py`。
- A 不直接改 `pages/profile` 做用户展示；用户页归 B。
- A 不修改 `pages/consultations`、`routes/user.py` 或 MySQL；B 不修改 chat/receipt/Agent/RAG 来保存记录。
- 不再新增或恢复任何底部四项导航，也不使用 `wx.switchTab`。
- 不复制公共导航栏/卡片样式形成 A、B 两套近似实现；不在功能提交里整文件格式化 `app.less`。
- A/B 都不要在没有同步文档的情况下改接口字段。
- 不把登录 token、手机号、VIN 明文写进日志或普通响应。
