# 01 · 需求与产品规格

> 本文档深度梳理「车小智要做成什么样」。所有功能点按当前需求边界拆解，标注 **A 主业务线** 与 **B 用户体系线**。
> 最新分工：A 负责现有首页/咨询/知识库/维修闭环；B 负责新增用户登录、个人资料、隐私信息和我的页个人数据。

---

## 1. 产品定位

**一句话**：车小智是面向**普通车主**的「车况翻译官 + 维修决策助手」。它把车主**听不懂、说不清、怕被坑**的维修场景，通过多智能体协同翻译成人话：

- 把**故障码**（P0300）翻译成大白话 + 风险等级 + 预估费用
- 把**口语症状**（"咕噜咕噜响"）关联到可能的故障与排查方向
- 把**维修报价**（"800 换机油机滤合理吗"）拿去和市场价比对，给出"合理/偏高/偏低警惕副厂件"的判断
- 把**报价单/部件图片**识别后给出参考（后续）
- 全程附**避坑建议**和**免责声明**，并把诊断结论沉淀成**维修记录**形成数据闭环

**目标用户**：不懂车、担心被维修店宰、希望先有个独立第三方判断再去修车的普通车主。

**核心价值**：信息不对称的修复 —— 让车主在进店前心里有数。

---

## 2. 界面总览

小程序共 4 个主界面 + 3 个辅助页：

| 类型 | 页面 | 路径 | 本期是否核心 |
|------|------|------|------|
| 主界面 | 首页 | `pages/index` | ✅ 入口 |
| 主界面 | 咨询（对话） | `pages/chat` | ⭐ **绝对核心** |
| 主界面 | 知识库 | `pages/kb` | ✅ 核心 |
| 主界面 | 我的 | `pages/profile` | ✅ B 用户体系 |
| 辅助 | 故障码详情 | `pages/detail` | ⚪ 当前写死 |
| 辅助 | 维修记录存根 | `pages/receipt` | ⚪ 当前写死 |
| 辅助 | 启动日志 | `pages/logs` | ⚪ 调试用，非业务 |

> 说明：当前**没有使用 `app.json` 的原生 tabBar**，四个 tab 的切换由各页面底部自绘导航 + `wx.redirectTo/navigateTo` 实现。这是后续要统一的一个点（见 04）。

## 3. 四个主界面功能点拆解

### 3.1 首页 `pages/index`

**定位**：功能入口与品牌展示。本身**不调任何后端接口**，是纯静态导航页。

**功能点：**

| 入口 | 行为 | 现状 |
|------|------|------|
| 顶部车辆卡片（车型/里程/位置/VIN） | 展示当前车辆 | 数据**写死**，应来自 `/api/context` |
| 「描述症状」入口 | 跳转咨询页 | ✅ 跳转可用 |
| 「故障码」入口 | 跳转故障码详情页 | ⚠️ 跳到写死的 P0300 详情 |
| 「拍照识别」入口 | 跳转咨询页 | ✅ 跳转可用 |
| 「报价审核」入口 | 跳转咨询页 | ✅ 跳转可用 |
| 快速开始案例（如"发动机咕噜""刹车片磨损""报价800元"） | 跳转咨询页 | ⚠️ 跳转可用，但携带的问题文本未真正带入对话框（见 04） |
| 底部 tab（咨询/知识库/我的） | 切换主界面 | ✅ 可用 |

**需求结论**：首页本期保持以导航为主即可。唯一需要打通的是**车辆卡片从 `/api/context` 取真实数据**（与咨询页共用同一上下文源），其余跳转入口已满足。

---

### 3.2 咨询页 `pages/chat` ⭐ 核心

**定位**：多智能体对话界面，是整个产品的核心载体。用户在这里用**文字 / 语音 / 图片**提问，得到结构化诊断结果。

**功能点：**

| 入口 | 行为 | 调用接口 | 现状 |
|------|------|----------|------|
| 进入页面 | 检测后端连通 | `GET /api/ping` | ✅ 已通 |
| 顶部车辆上下文卡片 | 展示车型/里程等 | 应来自 `GET /api/context` | ⚠️ 当前**写死在前端** |
| 文字输入 + 发送 | 提交问题、展示 AI 回复 | `POST /api/chat` | ⚠️ 能收发，但后端返回**占位文案**（见下方"核心问题"） |
| 快速询问芯片 | 一键提交预设问题 | `POST /api/chat` | ⚠️ 同上 |
| 语音按钮（按下录音） | 录音 → 转文字 → 填入输入框 | `POST /api/asr` | ✅ 已通（含降级占位） |
| 图片模式 | 以 `mode=image` 提问 | `POST /api/chat` | ⚠️ 后端仅回占位 |
| 连接状态条 | 主动重连检测 | `GET /api/ping` | ✅ 已通 |

**AI 回复需要展示的结构**（前端已实现渲染，后端需真实填充）：
- Agent 名称与描述（哪个智能体在回答）
- 处理步骤 `steps`（意图识别 → 分发 → 知识库检索 → 合成回复）
- 结论块 `blocks`（当前前端类型支持键值对 `kv` / 警告 `warn` / 高危 `danger`；`maintain` 里已有 `good` 输出，接入时需统一）
- 价格区间 `price_text` + `price_range`
- 免责声明 `legal_note`

**核心问题（需求层面必须知道）**：
当前 `POST /api/chat` 只做了**意图分类**（识别这是症状/故障码/报价/图片），然后返回一段**写死的占位文字**（"阶段 1 已完成路由，阶段 2 接入……"）。它**没有调用 maintain/dtc/symptom 等真正能查知识库、做 RAG、给价格判断的智能体**。所以咨询页目前给不出真实诊断。这是本期要打通的第一优先级，详见 [04](./04-当前进度与问题清单.md) 和 [05](./05-任务清单与开发计划.md)。

---

### 3.3 知识库页 `pages/kb`

**定位**：可检索的维修知识库。三类知识分 tab 浏览、搜索、筛选，并支持"一键咨询"跳回对话。

**功能点：**

| 入口 | 行为 | 调用接口 | 现状 |
|------|------|----------|------|
| 三个 tab（故障码/维修成本/症状关联） | 切换知识库类别 | `GET /api/kb/{dtc\|cost\|symptom}` | ✅ 已通 |
| 搜索框 + 搜索按钮 | 关键词检索（支持 DTC 精确码 / RAG 语义 / 子串三级） | `GET /api/kb/{kind}?q=` | ✅ 已通 |
| 高风险筛选 | 只看高风险条目 | `GET /api/kb/{kind}?level=high` | ✅ 已通 |
| 清空 / 刷新 | 重置或重载当前 tab | 同上 | ✅ 已通 |
| 列表项「一键咨询」 | 跳到咨询页并带上该条的提问文本 | 跳转 `pages/chat?ask=...` | ⚠️ 跳转有，但咨询页**未接收该参数**（见 04） |
| 分页 | 加载更多 | `page/page_size` | ⚠️ 前端写死 `page=1,page_size=50`，**分页未实现** |

**需求结论**：知识库**浏览/搜索链路是本项目当前最完整的一条后端链路**。它在本地模型和 `.chroma` 索引可用时走 RAG 语义检索，失败时自动降级到 JSON 子串匹配。需要补的是：① 一键咨询的参数传递；② 分页（数据少时可暂缓）。

### 3.4 我的页 `pages/profile` ✅ B 用户体系

**定位**：个人中心与用户账号入口。原先规划为本期不做，现在调整为**B 开发人员独立负责的新功能线**，包括用户登录、私人信息、个人资料、用户统计、车辆信息管理入口和隐私设置。

**现状**：
- 用户信息、统计数据、车辆信息**全部写死**。
- 6 个菜单项中**仅"我的维修记录"可跳转**到 `pages/receipt`（receipt 页也是写死数据）。
- 其余菜单项无任何绑定。

**B 本期要实现的功能点：**

| 功能 | 行为 | 建议接口 | 边界 |
|------|------|----------|------|
| 微信登录/游客登录 | 进入我的页时可登录，拿到稳定 `user_id` | `POST /api/user/login` | B 独立实现；A 只消费 `user_id` |
| 用户资料 | 昵称、头像、手机号授权状态、注册时间 | `GET/PATCH /api/user/profile` | B 独立实现 |
| 私人信息/隐私设置 | VIN 展示权限、手机号授权状态、数据清除入口 | `GET/PATCH /api/user/privacy` | B 独立实现，敏感字段默认脱敏 |
| 用户统计 | 咨询次数、维修记录数、预估节省金额 | `GET /api/user/stats` | B 聚合用户侧数据；A 不直接写 profile |
| 车辆信息管理入口 | 展示/编辑当前车辆，可与 `/api/context` 对齐 | `GET/PATCH /api/user/vehicle` 或复用 `/api/context` | 需在 03/06 明确字段，避免和 A 的 context 改动冲突 |
| 我的维修记录入口 | 跳转 `pages/receipt` 或展示用户维修记录列表 | `GET /api/user/repairs` | B 做列表入口；A 负责 `pages/receipt` 详情/存根页 |

**需求结论**：我的页从“不投入”调整为 **B 独立开发线**。为了避免冲突，B 只改 `pages/profile`、新增 `pages/login`/`pages/privacy`、新增用户 API 封装和用户后端服务；A 不在主业务任务中修改 `pages/profile`。

## 5. 端到端用户故事（目标态）

这是**打通后**应有的完整流程，也是 04/05 的验收基准：

```
车主进入首页
  → （可选）通过我的页完成登录，获得稳定 user_id
  → 点「咨询」进入对话页（顶部显示真实车辆上下文，来自 /api/context）
  → 输入「P0300 是什么意思」/ 语音 / 拍报价单
  → 前端 POST /api/chat
  → 后端 scheduler 识别意图（part / dtc / maintain / symptom / 综合；当前代码中 mode=image 优先）
  → 分发到对应智能体（LangGraph 编排）
      → 智能体调用 RAG 检索对应知识库（chroma 向量库，命中失败降级关键词/子串）
      → 智能体合成结构化结论（标题/通俗解释/风险等级/价格区间/避坑）
  → 后端把结构化结果按 03 契约返回
  → 前端卡片化展示，高风险红色强提醒
  → （可选）诊断结论沉淀为维修记录（add_receipt_item）
  → 用户可继续追问，或去知识库看详情，或生成维修存根
```

当前断在「**分发到对应智能体**」这一步：`/api/chat` 没有把请求交给智能体，而是直接回了占位文案。把这一步接上，是本期最核心的需求实现。

## 6. 非功能性需求与原则

- **永远能跑**：任何外部依赖（ASR 云服务、RAG 模型/索引）缺失时必须降级而非报错（ASR 返回占位文本、RAG 退回关键词/子串匹配）。当前后端已遵循此原则。
- **不编造**：智能体未命中知识库时，应返回"需要补充信息/澄清"，不得编造故障与价格。
- **合规**：每条诊断必须带免责声明 `legal_note`；VIN 必须脱敏（前 4 后 4，中间 `*`）。
- **隐私**：新增用户体系后，手机号、VIN、登录凭证、私人信息默认脱敏展示；B 负责用户隐私接口，A 的诊断链路只消费必要的 `user_id` 与车辆上下文，不直接处理手机号等敏感资料。
