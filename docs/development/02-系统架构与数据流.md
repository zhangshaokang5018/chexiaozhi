# 02 · 系统架构与数据流

> 本文档描述系统由哪些模块组成、各自职责、以及**数据是怎么流动的**——尤其是「前端点击 → 后端 → 智能体（LangGraph）→ RAG → 知识库 → 返回」这条主链路。

## 3. 核心数据流

### 3.1 对话主链路（目标态 vs 现状）

**目标态**（应该这样流）：

```
[前端] 用户发送 "800 换机油机滤合理吗"
   │  POST /api/chat  { user_id, text, mode, image_label }
   ▼
[routes/chat.py] 调 scheduler.route() 识别意图
   │  → 命中"报价/费用"关键词 → agent="maintain", confidence=0.9
   ▼
[agents/maintain.py]  handle(text, context)   ← 已接通
   │  LangGraph: extract → (关键词命中? assess : retrieve)
   │                         retrieve → rag.search("cost", text)
   │                         retrieve → (RAG命中? assess : clarify)
   │  assess: 算市场价区间、判报价高/低/合理、生成避坑、产出 receipt_item
   ▼
[services/rag.py]  向量检索 kb_cost (chroma, 距离≤0.55)
   ▼
[agents/maintain.py] 返回结构化 reply / steps / price_range / receipt_item
   ▼
[routes/chat.py] 按 03 契约组装 JSON 返回
   ▼
[前端] 卡片化展示：标题/通俗解释/价格区间/避坑/免责声明
```

**历史断点（已修复，保留用于追溯）**：

```
[前端] POST /api/chat
   ▼
[routes/chat.py] 调 scheduler.route() 识别意图   ✅ 正确
   ▼
[routes/chat.py] build_reply()  ← ❌ 直接返回写死占位文案
   │  "阶段 1 已完成路由，阶段 2 接入 XX 知识库详情……"
   ▼
[前端] 展示占位文字（无真实诊断、无价格、无 RAG）

  ⚠️ agents/maintain.py 的 handle() 从未被 chat.py 调用
  ⚠️ user_id 被前端发送但后端从未读取
  ⚠️ chat 链路从不触达 context / rag / 知识库
  ⚠️ maintain 返回的 miss/good 当前与前端 TS 类型不完全一致，接入时需同步规范
```

> **当前结论**：`chat.py` 已分发到 maintain/dtc/symptom/part，并完成 `miss/good` 输出归一。2026-06-28 新目标是在现有响应上补 `consultation_id/sources`，供 B 保存咨询快照。

### 3.2 知识库浏览链路（已打通，可作为参照范本）

```
[前端 kb 页] GET /api/kb/cost?q=机油&level=&page=1&page_size=50
   ▼
[routes/kb.py] load_kb("cost") → search_raw_kb()
   │  ① dtc 类先试 P 码精确匹配
   │  ② 调 rag.search() 语义检索 (距离≤0.55, 取前5)
   │  ③ RAG 无果 → JSON 子串匹配兜底
   ▼
[services/rag.py] chroma 向量检索（失败则返回 None 触发降级）
   ▼
[routes/kb.py] normalize_item() 规范化 + 分页 + 组装 tabs
   ▼
[前端] 列表渲染；点击"一键咨询"应跳回 chat
```

这条链路真实地走完了「接口 → 知识库 → 返回」，并且在本地模型与 `.chroma` 索引可用时会经过 RAG 语义检索；索引缺失或模型不可用时会自动降级到 JSON 子串匹配。因此它是当前最完整的后端知识库链路，但不能把“每次搜索都一定经过 RAG”作为验收前提。

### 3.3 语音输入链路（已打通）

```
[前端] 录音 → wx.uploadFile POST /api/asr (file 字段, mp3/16k/单声道)
   ▼
[routes/asr.py] → services/asr.transcribe()
   │  有 DASHSCOPE_API_KEY → 阿里云百炼 paraformer 真实识别
   │  无 Key / 失败 → 返回占位文本, simulated=true
   ▼
[前端] 把识别文本填入输入框，由用户确认后再走 /api/chat
```

### 3.4 上下文与维修存根链路（A 前端已接，持久化待 B）

```
[services/context.py] 内存 _STORE[user_id] = { context, receipt_items }
   ├ GET  /api/context?user_id=  → 返回脱敏车辆信息 + receipts
   ├ POST /api/context           → 返回 { ok, context }
   └ 智能体诊断后 add_receipt_item() 沉淀诊断项
[services/receipt.py] build_receipt(user_id) → 汇总 receipt_items 成核销单
   └ POST /api/receipt → { shop, items, total, vin(脱敏), simulated }

  ✅ A 的 chat/index/receipt 已调用对应接口。
  ⚠️ context 仍是进程内状态；长期维修记录需要 B 的 user_repairs 持久化。
```

### 3.5 用户体系链路（B 新增，独立于 A 主链路）

```
[我的页 profile] 进入页面
   │  无登录态 → 展示登录入口
   │  有登录态 → GET /api/user/profile + GET /api/user/stats
   ▼
[routes/user.py] 用户接口层（B）
   ├ POST  /api/user/login       微信 code/游客登录 → user_id/session_token
   ├ GET   /api/user/profile     用户资料
   ├ PATCH /api/user/profile     更新昵称/头像等非敏感资料
   ├ GET   /api/user/privacy     隐私设置与授权状态
   ├ PATCH /api/user/privacy     更新隐私开关/清除授权
   ├ GET   /api/user/stats       咨询次数/维修记录数/节省金额
   ├ GET/PATCH /api/user/vehicle 当前车辆资料
   ├ GET/POST /api/user/consultations 咨询记录快照
   └ GET/POST /api/user/repairs 维修记录快照
   ▼
[services/user.py] 用户数据读写与脱敏（B）
   ▼
[services/db.py → MySQL chexiaozhi_user]
   users / user_privacy / user_vehicle / user_stats / user_consultations / user_repairs
   │  惰性连接：首次查询才连库；MySQL 未启动时仅用户接口报错，不影响 A
   ▼
[A 主业务链路] 只消费稳定 user_id；不直接读手机号、登录凭证等私人信息
```

并行开发边界：B 独立完成用户接口、profile/login/privacy/consultations 页面与 `utils/user-api.ts`；A 的 chat/context/receipt 继续支持 `user_id`，并提供可持久化的 `consultation_id/sources/receipt_id`。详细交界与合并顺序见 [06](./06-并行开发边界与合并规则.md) 和 [07](./07-2026-06-28页面与记录增量变更.md)。

### 3.6 咨询记录与维修记录持久化（2026-06-28 新增）

```text
A /api/chat → Agent → RAG/知识库 → 结构化响应 + consultation_id + sources
   └ 前端 chat 展示成功后，非阻塞调用 B POST /api/user/consultations
      └ MySQL user_consultations 保存当次快照

A /api/receipt → 维修存根 + receipt_id
   └ 前端 receipt 展示成功后，非阻塞调用 B POST /api/user/repairs
      └ MySQL user_repairs 保存当次快照
```

两条写入都必须幂等：分别以 `consultation_id`、`receipt_id` 为唯一业务键。同一页面重复进入或网络重试不得产生重复记录。B 接口失败只影响历史持久化，不得阻断 A 的当前聊天、RAG、知识库和存根展示。

### 3.7 页面导航（2026-06-28 新增）

最终产品不使用 `app.json` 原生 tabBar，也不保留页面自绘四项导航。首页左上角菜单进入 profile；profile 的“我的维修记录”进入 receipt，“咨询记录”进入 consultations。普通进入使用 `navigateTo`，返回使用 `navigateBack`，不再使用 `switchTab`。

## 4. 技术栈与关键依赖

**后端**（`car-server/requirements.txt`，均为真实依赖）：
- `Flask>=3.0` + `flask-cors>=4.0`：Web 框架，CORS 开发期全开放
- `langgraph>=1.2`：智能体编排（maintain 真实使用 StateGraph）
- `chromadb>=0.5`：本地向量库，持久化到 `.chroma/`
- `sentence-transformers>=3.0`：embedding 模型 `BAAI/bge-small-zh-v1.5`（中文，约 100MB）
- `dashscope>=1.20`：阿里云百炼（ASR，可选）

**前端**：微信原生小程序（TypeScript + GlassEasel 组件），无额外框架。

**B 用户体系存储**（与 A 隔离，A 不依赖）：
- 本地 **MySQL 8.x**，库名 `chexiaozhi_user`；当前脚本已有 4 张基础表，B 按 2026-06-28 增量再新增 `user_consultations`、`user_repairs`，目标共 6 张表，见 [03 §11](./03-接口契约.md)
- 驱动 `PyMySQL>=1.1` + `python-dotenv>=1.0`，列在 B 独占的 `requirements-user.txt`（不入 `requirements.txt`）
- 连接配置走 `.env` 的 `DB_*`（`.env.example` 已预留）；`services/db.py` 惰性连接

**RAG 关键参数**：
- 模型：`BAAI/bge-small-zh-v1.5`
- 查询指令前缀：`为这个句子生成表示以用于检索相关文章：`
- 命中距离阈值：`0.55`（maintain 取 top_k=1；kb 搜索取 top_k=5）
- 失败策略：模型缺失/索引缺失/查询异常 → 返回 `None`，调用方降级到关键词/子串

## 6. 本地启动（速查）

> 详细环境搭建以 `car-server/README.md` 为准，此处仅给联调最小步骤。

**后端**：
```bash
cd car-server
python -m venv .venv && source .venv/Scripts/activate   # Windows Git Bash
pip install -r requirements.txt
python -m services.rag build      # 首次构建向量索引（可选，失败会自动降级）
python app.py                     # 监听 0.0.0.0:5000
```

**B 用户体系数据库（仅 B 需要，A 可跳过）**：
```bash
cd car-server
pip install -r requirements-user.txt
mysql -u root -p < sql/user_schema.sql
mysql -u root -p -e "CREATE USER IF NOT EXISTS 'cxz_user'@'localhost' IDENTIFIED BY 'cxz_user_dev_2026'; CREATE USER IF NOT EXISTS 'cxz_user'@'127.0.0.1' IDENTIFIED BY 'cxz_user_dev_2026'; GRANT SELECT, INSERT, UPDATE, DELETE ON chexiaozhi_user.* TO 'cxz_user'@'localhost'; GRANT SELECT, INSERT, UPDATE, DELETE ON chexiaozhi_user.* TO 'cxz_user'@'127.0.0.1'; FLUSH PRIVILEGES;"
mysql -u root -p -e "USE chexiaozhi_user; SHOW TABLES;"
mysql -u root -p -e "USE chexiaozhi_user; SELECT user_id,nickname FROM users;"
mysql -h 127.0.0.1 -u cxz_user -pcxz_user_dev_2026 -e "USE chexiaozhi_user; SELECT user_id,nickname FROM users WHERE user_id='user_10001';"
```

当前 `user_schema.sql` 会创建四张基础表，并初始化演示用户 `user_10001`、默认隐私设置、演示车辆和演示统计。B 按 2026-06-28 增量新增 `user_consultations`、`user_repairs` 及演示记录后，目标为六张表。B 本地联调用固定数据库账号 `cxz_user`、密码 `cxz_user_dev_2026`、库名 `chexiaozhi_user`；root 只用于建库和授权。然后复制 `car-server/.env.example` 为 `car-server/.env`，填写 `DB_HOST=127.0.0.1`、`DB_PORT=3306`、`DB_USER=cxz_user`、`DB_PASSWORD=cxz_user_dev_2026`、`DB_NAME=chexiaozhi_user`。业务演示用户是 `user_10001`，当前 MVP 是微信/游客登录模型，没有业务密码字段。`services/db.py` 必须惰性连接 MySQL：服务启动时不连库，只有 `/api/user/*` 被调用时才查询数据库。这样 A 的 `/api/chat`、`/api/kb` 等主业务不受 MySQL 是否安装/启动影响。

**前端**：
1. 微信开发者工具打开 `car-miniapp`
2. 「详情 → 本地设置」勾选「不校验合法域名…」
3. 真机预览时把 `utils/request.ts` 的 `BASE_URL` 改成电脑局域网 IP
